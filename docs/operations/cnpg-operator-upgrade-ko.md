# CloudNativePG 오퍼레이터와 Barman 플러그인 업그레이드 (0.29.1과 0.8.1)

English version: [cnpg-operator-upgrade.md](cnpg-operator-upgrade.md)

## 개요

| 차트 | 이전 | 이후 | 애플리케이션 버전 |
|------|------|------|-------------------|
| `cloudnative-pg` | 0.29.0 | 0.29.1 | 오퍼레이터 1.30.0에서 1.30.1 |
| `plugin-barman-cloud` | 0.7.1 | 0.8.1 | 플러그인 v0.14.0에서 v0.15.1 |

두 차트 모두 이 저장소의 `extraResources` 패치를 유지합니다. 이전 업스트림 대비
이전 패치를 추출해서 새 차트에 적용했으므로 변경 범위가 동일합니다(`PATCH.md`,
`templates/extra-resources.yaml`, `values.yaml`의 한 블록).

## 호환성

| 질문 | 답 | 근거 |
|------|----|------|
| 플러그인이 오퍼레이터 1.30을 지원하나? | 예. 플러그인은 오퍼레이터 1.26 이상이 필요 | 플러그인 설치 문서 |
| 플러그인에 cert-manager가 필요한가? | 예, 설치되어 있음 | 차트 README |
| 플러그인 차트의 최소 쿠버네티스 | 1.29 | 차트 `kubeVersion` |
| "0.8.x"의 이름 변경 호환성 깨짐? | 플러그인 애플리케이션 v0.8.0(2025-10-27)의 일로 이미 지났습니다. 차트 0.8.1과 무관하고 배포는 이미 새 이름을 씁니다 | 플러그인 릴리스 v0.8.0 |
| DB가 PostgreSQL 이미지를 고정했나? | 예. 4개 클러스터 모두 `imageName`을 지정해서 오퍼레이터의 새 기본값(18.6)이 적용되지 않습니다 | 라이브 클러스터 |
| Barman 플러그인을 쓰는 클러스터가 있나? | 없음(4개 모두 `plugins`가 비어 있음) | 라이브 클러스터 |

## 바뀌는 것

오퍼레이터 차트:

- 이미지 1.30.0에서 1.30.1. 정체될 수 있던 페일오버, 펜싱된 인스턴스가 재생성을 막던 문제, 웹훅 경로 검사 수정이 포함됩니다.
- 새 값 `scratchData.emptyDir`, 기본값 `{}`는 이전에 하드코딩된 값과 같습니다.
- CRD: `restoreAdditionalCommandArgs` 추가와 설명 수정. `Pooler`에 `minimum: 0` 검사가 붙지만 `Pooler`는 없습니다.
- RBAC은 그대로입니다.

플러그인 차트:

- 이미지 v0.14.0에서 v0.15.1(Barman 3.20).
- 새 값 `logLevel`, 기본값 `info`. 이전 차트는 `debug`로 하드코딩되어 있었으므로 플러그인 로그가 조용해집니다. 이전 출력을 유지하려면 `logLevel: debug`로 지정합니다.
- CRD 설명 한 줄 수정.

## 오퍼레이터 업그레이드는 모든 PostgreSQL 인스턴스를 재시작합니다

오퍼레이터 컨트롤러가 갱신되면 CloudNativePG가 새 인스턴스 매니저를 각 PostgreSQL
파드에 반영합니다. 기본은 롤링 업데이트이고 클러스터마다 스위치오버로 끝나며,
모든 클러스터가 동시에 진행됩니다. 클러스터 4개에 인스턴스가 각 3개이고, 데이터는
USB 드라이브 한 개의 NFS를 함께 씁니다.

이 변경은 롤아웃을 분산하는 문서화된 오퍼레이터 설정 두 개를 추가합니다.

| 키 | 값 | 의미 |
|----|----|------|
| `CLUSTERS_ROLLOUT_DELAY` | 120 | 서로 다른 클러스터 사이 대기(초) |
| `INSTANCES_ROLLOUT_DELAY` | 30 | 한 클러스터 안 인스턴스 사이 대기(초) |

`ENABLE_INSTANCE_MANAGER_INPLACE_UPDATES`(재시작 없는 제자리 갱신)도 문서화되어
있지만 기본 동작을 유지하려고 켜지 않았습니다.

## 롤아웃 순서

1. cert-manager 업그레이드를 먼저 병합하고 이슈어가 `Ready`가 될 때까지 기다립니다. 플러그인은 cert-manager로 인증서를 발급받습니다.
2. DB 클러스터 4개가 모두 `Cluster in healthy state`이고 복제본이 모두 스트리밍 중인지 확인합니다. 복구에 걸린 복제본이 있으면 롤링 업데이트가 더 나빠지므로 먼저 재복제합니다.
3. 플러그인 차트만 먼저 올립니다. 쓰는 클러스터가 없어 데이터에 영향이 없습니다.
4. 오퍼레이터 차트를 단독으로, 한가한 시간에 올립니다. 오퍼레이터 파드 2개가 교체되고, 이어 클러스터들이 차례로 짧은 스위치오버와 함께 갱신됩니다.
5. 모든 클러스터가 다시 healthy가 될 때까지 지켜봅니다.

```sh
kubectl get cluster.postgresql.cnpg.io -A -w
```

## 롤백

- 플러그인: 커밋을 되돌립니다. 상태가 없습니다.
- 오퍼레이터: 커밋을 되돌립니다. CRD 변경은 추가형이라 이전 오퍼레이터도 객체를 받아들입니다. 인스턴스 매니저가 다시 바뀌므로 PostgreSQL 파드가 같은 간격으로 한 번 더 롤링됩니다.
- 롤링 후 클러스터가 정상으로 돌아오지 않으면 일반적인 멈춘 복제본처럼 다룹니다. 먼저 파드 로그를 보고, 복구가 진행되지 않을 때만 복제본을 재복제(파드와 PVC 삭제)합니다.

## 시험

| 확인 | 결과 |
|------|------|
| Application 값으로 두 차트 `helm lint`, `helm template` | 통과 |
| 이전과 새 버전의 리소스 목록(29개와 20개) | 동일 |
| `extraResources` 훅의 객체 형식과 문자열 형식, 이전과 새 차트 | 두 형식 모두 렌더링되고 네임스페이스 표현식이 평가됨 |
| 라이브 클러스터 대비 `kubectl diff` | 이미지 태그, CRD 추가, 플러그인 `info` 로그 수준과 사이드카 이미지. RBAC과 Service 변경 없음 |
| 일회용 클러스터에서 오퍼레이터 롤링 재시작 | **실행하지 않음.** 작업 PC 디스크가 거의 가득 찼고 공유 컨테이너 VM의 여유가 부족했습니다. 동작은 업스트림 문서에 근거합니다 |
