# LiteLLM 차트와 프록시 이미지: 지금은 분리해 둡니다

English version: [litellm-chart-image-alignment.md](litellm-chart-image-alignment.md)

## 갱신: 이미지를 v1.103.5로 맞췄습니다

아래 선행 조건을 충족해 이미지를 차트와 같은 `v1.103.5`로 올렸습니다. 근거는
"이미지 업그레이드 시험"에 있습니다. 그 뒤의 절들은 이전에 분리하기로 한
이유를 그대로 남긴 것입니다.

## 결정 (이전)

- **차트는 지금 올립니다.** `1.98.0`에서 `1.103.5`로.
- **프록시 이미지는 `v1.89.4`로 의도적으로 고정**해 둡니다. 이미지 업그레이드는 DB를 마이그레이션하고 그 마이그레이션은 되돌릴 수 없으므로, 별도 계획을 가진 별도 변경으로 다룹니다.

업스트림에서는 차트와 이미지가 같은 버전으로 움직이지만, 이 Application은 차트
`1.98.0` 이전부터 이미지를 덮어써 왔습니다. 차트 업그레이드는 그것을 바꾸지 않고
템플릿만 최신으로 맞춥니다.

## 고정된 이미지에서 차트 업그레이드가 안전한 이유

Application 값을 두 차트에 같은 이미지 태그로 렌더링해 비교했습니다.

| 확인 | 결과 |
|------|------|
| 리소스 목록 | 동일, 11개 |
| 렌더링 차이 | `helm.sh/chart`와 `app.kubernetes.io/version` 라벨, 빈 줄 하나뿐 |
| Deployment의 이미지 | 둘 다 `ghcr.io/berriai/litellm:v1.89.4` |
| 라이브 클러스터 대비 `kubectl diff` | `litellm` Deployment와 Service의 라벨뿐. 나머지는 Argo CD 추적 주석만 다름 |
| 벤더링 복사본 | 업스트림 원본과 동일. 로컬 패치 없음, 차트가 `extraResources`를 기본 지원 |

Deployment의 파드 템플릿 라벨이 바뀌므로 `litellm` 파드가 한 번 롤링됩니다(복제본
2개, `maxUnavailable: 0`). 버전 라벨은 `1.103.5`로, 이미지는 `v1.89.4`로 표시됩니다.
이 불일치는 외형일 뿐이며 분리 상태를 보여 주는 표시입니다.

업스트림 템플릿 변경은 작습니다. 환경 변수 블록이 출력 변화 없이 헬퍼로 옮겨졌고,
마이그레이션 Job에 선택적 `activeDeadlineSeconds`가 생겼고, 마스터 키 Secret이
`lookup`으로 기존 키를 재사용하며(Argo CD는 클러스터 접근 없이 렌더링하고 이
Application은 자체 마스터 키 Secret을 제공합니다), 메트릭 Service와 컬렉터 옵션이
추가되었습니다.

## 이미지 업그레이드를 따로 하는 이유

`v1.89.4`에서 `v1.103.5` 사이에 업스트림이 **DB 마이그레이션 57개**를 추가했고
제거한 것은 없습니다. 마이그레이션 SQL로 확인한 내용입니다.

| 종류 | 개수 |
|------|------|
| `ADD COLUMN` | 40 |
| `CREATE TABLE` | 14 |
| `CONCURRENTLY` 없는 `CREATE INDEX` | 11 |
| `DROP`, `RENAME`, 데이터 `UPDATE`나 `DELETE` | 소수, 대부분 같은 구간에서 만들어진 `shadow_eval_*` 테이블 |

대부분 추가형입니다. 남는 위험은 이렇습니다.

1. `SpendLogs` 같은 테이블의 인덱스 생성은 만드는 동안 잠금을 잡습니다. 이 DB에서 그
   테이블 크기는 **측정하지 않았습니다**.
2. 이 Application은 `migrationJob.enabled: false`라서 프록시가 시작하면서 직접
   마이그레이션합니다. 롤링 중에는 구 버전 파드가 마이그레이션된 스키마를 보게 됩니다.
3. DB는 앞으로만 갑니다. 오브젝트 스토리지를 통한 백업이 없습니다.

이 구간 안정판 릴리스 노트에는 명시적인 호환성 깨짐이 없지만, 자동 생성된 PR
목록이라 약한 증거입니다.

## 이미지 업그레이드 전에

1. `litellm` 데이터베이스에서 가장 큰 테이블의 크기와 행 수 추정치를 측정합니다.
2. 논리 덤프(`pg_dump`)를 만들고 임시 데이터베이스에 복원되는지 증명합니다.
3. 전용 마이그레이션 실행을 권합니다. 업그레이드 동안 `migrationJob`을 켜고 기본
   `activeDeadlineSeconds: 1800`을 유지하거나, 롤링 동안 복제본을 1개로 줄입니다.
4. 구간 안 모든 안정판 릴리스 노트에서 `proxy_config`와 `litellm_settings`에 쓰는
   설정 키 변경을 확인합니다.
5. 한가한 시간을 고릅니다. 클러스터 안에서는 Hermes Agent가 이 프록시를 호출하고 컨텍스트 숫자를 자체 사본으로 따로 갖고 있으므로, 모델을 바꾼 뒤에는 그 사본이 `model_info`와 맞는지 확인합니다.

## 스모크 테스트 계획 (이미지를 바꾼 뒤 항상)

1. `kubectl rollout status deploy/litellm`이 끝나고 파드 2개가 Ready.
2. `/health/readiness`와 `/health/liveliness`가 200.
3. `/v1/models`가 `model_list`의 모든 `model_name`을 나열.
4. `/model/info`가 `max_input_tokens`를 정의한 항목에서 값을 보여 줌.
5. 공급자 경로마다 채팅 완료 한 건: NVIDIA NIM, Upstage, 이미지와 임베딩 모델.
6. UI 로그인이 되고 가상 키 페이지가 열림. 테스트 키를 만들고 삭제.
7. 완료 요청 뒤 spend 로그에 행이 생김.
8. Hermes Agent가 여전히 프록시에 접속됨.
9. 파드 로그에 마이그레이션이나 Prisma 오류가 없음. `_prisma_migrations`의 모든 행이 완료.

## 이미지 업그레이드 시험 (2026-10-27)

운영 DB를 덤프해서 임시 PostgreSQL 18 컨테이너에 복원했습니다. 그 복사본에 라이브
`config.yaml`로 LiteLLM `v1.103.5`를 붙였고, `v1.89.4`는 원본과 마이그레이션된
복사본 양쪽에 붙였습니다.

| 질문 | 결과 |
|------|------|
| DB 크기 | 전체 17MB. 가장 큰 테이블인 spend 로그가 약 1,200행에 4MB라서 인덱스 생성이 오래 잠금을 잡을 수 없음 |
| 덤프가 완전히 복원되나? | 예. `pg_restore --exit-on-error`가 성공했고 모든 테이블의 행 수가 운영과 같음 |
| 마이그레이션 57개가 적용되나? | 예, 약 1초. 적용 186개, 미완료 0, 롤백 0 |
| 기존 데이터가 사라지나? | 아니오. 기존에 있던 모든 테이블의 행 수가 동일 |
| 새 이미지가 그 데이터에서 동작하나? | 예. 모델 15개, `max_input_tokens` 보존, 완료 요청 3건, 키 생성과 삭제, spend 로그 기록 |
| 구 파드가 마이그레이션된 스키마에서 돌 수 있나(롤링)? | 예. `v1.89.4`는 펜딩 마이그레이션이 없다고 보고하고 healthy이며 모델, 완료 요청, 키 생성이 됨 |
| 시작 로그의 설정 키 경고 | 두 이미지 모두 없음 |
| 시작 시간 | 두 이미지 모두 로컬에서 약 205~220초. Copilot 모델이 기기 인증을 기다리기 때문입니다. 프로브 예산은 300초입니다. 운영은 토큰을 마운트해서 더 빠릅니다 |

`migrationJob`은 계속 꺼 둡니다. 마이그레이션이 약 1초 걸리고 구 파드가 새
스키마에서 계속 동작하므로 전용 Job이 얻는 것이 없습니다.

## 롤백

- 차트: 커밋을 되돌립니다. 상태가 있는 변경이 없습니다.
- 이미지: 새 파드가 마이그레이션을 시작하기 전에만 가능합니다. 시작한 뒤에는 업그레이드
  직전에 만든 덤프로 복원하고 태그를 되돌립니다. 복원은 시험했습니다.

## 더 새로운 차트가 있습니다

준비하는 동안 레지스트리에 차트 `1.106.4`가 이미 올라와 있었습니다. 이 변경은
이슈의 목표(`1.103.5`)를 따랐고, 같은 렌더링 비교를 이후 차트에도 반복할 수 있습니다.
